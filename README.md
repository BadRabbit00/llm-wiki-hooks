# hooks — хуки для агентов

Эталонные фрагменты конфигурации. `wk init` раскладывает их в проект; версионируются
вместе с проектом. Контракт подкоманд `wk hook` — в `../llm-wiki/fix.md`, раздел A1.

Хук — это команда, а не текст. Он либо проходит, либо блокирует. Хук не редактирует файлы,
не обращается к сети без нужды и не печатает ничего, кроме причины отказа.

## Почему claude/ и codex/ в каждой папке

Контракт исполнения у харнессов **совпадает**, файл-контейнер — **нет**.

| | claude-code | codex |
|---|---|---|
| файл в проекте | `.claude/settings.json` | `.codex/hooks.json` |
| корень | `hooks` — один из ключей общих настроек | `hooks` + необязательный `description` |
| структура | `{событие: [{matcher, hooks: [{type, command, timeout}]}]}` | та же |
| payload | JSON на stdin | JSON на stdin |
| общие поля payload | `session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input` | те же |
| код 0 | успех, JSON со stdout читается | успех, JSON со stdout читается |
| код 2 | блокирующее решение, причина в stderr | то же |
| прочий код | неблокирующая ошибка, работа продолжается | то же |
| события, которые нужны нам | `PreToolUse`, `Stop`, `SessionStart` | те же |
| личные настройки вне git | `.claude/settings.local.json` | `~/.codex/hooks.json` |

Поэтому содержимое групп хуков в обоих файлах байт в байт одно и то же, а разнесено по
двум папкам ровно из-за контейнера: `description` в `.claude/settings.json` — лишний ключ,
а `.codex/hooks.json` не место для остальных настроек claude-code.

Чего в codex нет и на что опираться нельзя: `${CLAUDE_PROJECT_DIR}` и прочие подстановки путей,
типы хуков `http`, `prompt`, `agent`, поля `if`, `once`, `args`, `asyncRewake`.
Наши хуки — только `type: "command"` с одной командой `wk`, и это не стилистика,
а условие переносимости.

## Состав

| папка | событие | команда | поведение |
|---|---|---|---|
| `check-on-stop` | `Stop` | `wk hook check` | проверки не прошли → код 2, ход не завершается |
| `guard-policy-block` | `PreToolUse` | `wk hook guard-block` | правка внутри блока политик → код 2 |
| `guard-checker` | `PreToolUse` | `wk hook guard-paths` | запись в чекер или конфиг хуков → код 2 |
| `policy-staleness` | `SessionStart` | `wk hook policy-stale` | блок устарел → одна строка, не блокирует |

Собранные файлы для раскладки — в `install/`.

## Состояние реализации в `wk`

Задачи 02, 06 и 07A сделаны: `wk check`, `wk check --strict`, `wk docs check`,
`wk policy sync` и `wk policy check` работают и покрыты golden-тестами против исходного
`check.py` и настоящего `export_block`.

Все четыре подкоманды `hook` реализованы в `wk/internal/wk/hooks.go`.
`wk init` доставляет встроенные копии конфигураций, включая offline-режим;
существующие конфиги сохраняются с diff. Тесты проверяют блокировки, stdin,
офлайн, `stop_hook_active`, JSON контекста и отсутствие записи из хуков.

Чего делать нельзя: подменять `wk hook check` на `wk check --strict` в группе `Stop`.
Блокирует только код 2, а `wk check --strict` даёт 1 при ошибках и 3 без сети —
гейт станет украшением. Обоснование — в задаче 04, пункт 1.

## Три решения, которых не было в первой редакции задачи 04

Все три описаны в `../llm-wiki/fix.md`, раздел A1. Здесь — кратко, чтобы фрагменты
читались без него.

1. **Путь к файлу приходит на stdin, а не аргументом.** Первая редакция задачи требовала
   `wk hook guard-block --file <path>`. Подстановки значений payload в аргументы команды
   нет ни у одного харнесса: у claude-code `${...}` работает только для `type: "mcp_tool"`,
   у codex команда получает тот же JSON на stdin. Все хук-команды читают JSON со stdin.
2. **`.codex/hooks.json` входит в список защищённых путей.** Иначе пункт 3 задачи
   не выполняется на codex: защита снимается удалением собственного конфига.
3. **На `SessionStart` вызывается `wk hook policy-stale`, а не `wk policy check`.**
   Хук обязан всегда возвращать 0 и доставлять текст через
   `hookSpecificOutput.additionalContext`. Подробности — в `policy-staleness/README.md`.

## Требования к любому новому хуку

- только `wk`. Никаких `python`, `jq`, `sed`, многострочных shell-скриптов внутри JSON;
- хуки записи — не дольше 5 секунд и без сети;
- `check` и `policy-stale` спрашивают у вики версию блока политик: `timeout` 10,
  недоступная сеть — код 0, а не отказ;
- нет манифеста `.wiki-project.yaml` — молча код 0: в непроектных репозиториях хук не мешает;
- текст отказа — одна строка с конкретным действием;
- неизвестные поля payload игнорируются: состав у харнессов различается и растёт;
- хук не делает `wk policy sync` и не коммитит;
- хук не блокирует файлы, не перечисленные в задаче.

## Для агентов без хуков

Те же проверки ставятся в CI проекта обязательным шагом `wk check --strict`.
Обратная связь медленнее, непробиваемость та же. Для codex гейт на остановке дублируется
в CI всегда. Матчер записи защищает инструменты с `tool_input.file_path`;
shell и собственный `apply_patch` Codex в этот набор не входят. В офлайне гейт
пропускает ход намеренно — там проверку обеспечивает CI.

`statusMessage` подтверждён [документацией Codex](https://learn.chatgpt.com/docs/hooks)
9 октября 2026 и сохранён. Пользователь доверяет установленным хукам через `/hooks`.
